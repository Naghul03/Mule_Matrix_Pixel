MULE MATRIX
End-to-End MVP Build Specification
A simulation-first, explainable system for detecting suspected mule accounts and reconstructing cross-bank transaction lineage
Implementation handoff for Antigravity

0. Build mandate
Build a fully runnable local prototype—not a mockup—using synthetic data. The system must let a user initiate transfers, observe simulated multi-bank transaction events, detect accounts with explainable evidence, and reconstruct the likely flow of funds backward and forward through account networks until an off-ramp, a terminal point, a configured investigation limit, or an explicitly uncertain boundary is reached.
This document is the source of truth. Implement the requirements in order, keep the project runnable at every phase, and do not replace core functionality with static screenshots, hardcoded dashboard numbers, or buttons that do nothing.
1. Product goal and non-goals
Primary goal
Detect and flag a suspected mule account using explicit, inspectable signals; never flag an account without a recorded reason.
After a trigger, trace related transfers across banks and payment rails in the synthetic environment, including partial amounts, splits, merges, repeated hops, and long chains.
Display a lineage evidence trail: accounts, banks, transactions, timestamps, amounts, detection reasons, confidence/uncertainty, and why the trace stopped.
Support cases with no off-ramp. An off-ramp is one possible terminal event, not a prerequisite for detection or tracing.
Demonstrate the system through an interactive transaction simulator and a visual investigation workspace.
Non-goals / honesty boundaries
Do not connect to real bank systems, real customer records, or live RBI systems. All records are synthetic and clearly labeled as such.
Do not claim that e₹ programmability automatically enables universal tracing across banks. In this prototype, cross-bank visibility exists because the simulator provides a shared synthetic event/ledger feed.
Do not label someone a criminal. Use “suspected mule”, “risk signal”, and “requires review”; detection is not proof of wrongdoing.
Do not claim novelty or superior performance until measured against documented baseline rules on held-out test scenarios.
Do not implement real token issuance, blockchain, CBDC wallet integration, or actual off-ramp access. Simulate those concepts as events.
2. User journeys
Demo mode: choose a scenario, start it, watch transfers occur, see alerts appear with reasons, and follow the investigation live.
Manual transfer mode: choose source/destination accounts, enter an amount and optional memo, submit a simulated transfer, then observe the ledger and any detector response.
Investigations mode: open an alert, inspect evidence, run backward/forward tracing, view the network graph and lineage timeline, and export a case report.
Scenario lab: select normal or suspicious scenarios, change speed/thresholds, reset the simulation, and compare expected ground truth with system output.
Evaluation mode: run the test suite and see precision, recall, false-positive rate, path/lineage recovery, runtime, and baseline comparison.

4. System overview
Core flow:
Scenario / Manual Transfer → Transaction API → Ledger + Event → Detection Engine → Alert / Trigger → Lineage Engine → Investigation Graph + Timeline → Case Report
Separate these responsibilities in code:
Ledger: records what the simulator says happened. Never rewrite posted transactions; use reversal/adjustment events.
Detection: evaluates account/transaction/network signals and records reasons. It does not decide the lineage by itself.
Lineage: reconstructs candidate paths from the ledger and reports evidence plus uncertainty. It does not declare guilt.
Ground truth: scenario generator stores hidden labels used only for evaluation, not exposed as detector inputs.
Presentation: reads API results; never computes authoritative risk or lineage solely in the browser.

Important modeling rules
Accounts belong to banks; transactions reference source and destination accounts. A cross-bank transfer is simply a transaction whose endpoints have different bank IDs.
Keep transaction status and lifecycle events. Pending, failed, duplicated, reversed, and late-arriving events must not be treated as settled money movement.
The prototype’s default model is a transfer ledger, not a claim that each fungible digital-currency unit can always be identified. Partial-transfer lineage is an attribution estimate unless the simulation explicitly provides token/lot-level provenance.
For realistic splits/merges, optionally add TransferAllocation(source_transaction_id, downstream_transaction_id, allocated_amount_minor, method, confidence). Enforce that allocations never exceed the source or downstream amount.
Use synthetic stable account references and generated names only. No real account numbers or personal identifiers.
Enforce unique idempotency keys; use database constraints for positive amounts, valid currency, valid endpoints, and valid state transitions.
6. Detection: what makes an account suspicious?
No account is flagged merely because it is connected to another account or because it receives a large amount. Every alert must include one or more observable signals, a rule code, the evidence window, and a human-readable explanation.
Signal family
Example feature
Important guardrail
Pass-through behavior
High inbound value followed by rapid outbound value; low retained balance in a time window
Compare to account type and normal behavior; do not use one universal threshold.
Fan-in / fan-out
Many unrelated sources converge on one account, then funds disperse to many destinations
Count unique counterparties and time windows; legitimate aggregators exist.
Velocity / burst
Transaction count or value spikes compared with the account’s recent baseline
Synthetic prototype may use configurable limits; show the exact window.
Repeated small retention
Repeated transfers leave a similar small fraction behind while the rest moves onward
Use as a supporting signal only; avoid treating a single percentage as proof.
Network context
Account is part of a multi-hop cluster with multiple independent risk signals
Propagate risk carefully; a connection alone is not enough.
Identity / lifecycle anomalies
New account rapidly begins high-volume pass-through activity
Synthetic metadata only; explain the feature and avoid protected-class proxies.
Known scenario indicator
Simulator marks an event as off-ramp or known mule role
Allowed for demo labels only if clearly separated from operational detector inputs; do not leak ground truth into detection.

Implement a deterministic rule-based baseline first. Use configurable, versioned rules and a risk score that is the sum of bounded, documented contributions. Set alert thresholds through configuration. Each alert should show the contributing rules and raw evidence. Do not use an LLM to decide whether an account is a mule.
Baseline and proposed innovation
Baseline: account-level threshold and velocity rules, pass-through ratio, fan-in/fan-out, and short time-window patterns.
Candidate Mule Matrix contribution: trigger-based cross-bank lineage reconstruction with split/merge-aware amount attribution, evidence-linked graph exploration, and explicit uncertainty/stop reasons.
Only call this a demonstrated improvement if evaluation shows a measurable gain on held-out scenarios versus baseline. State the exact metric and test set.
Use a common interface for detector versions so baseline and candidate can be compared fairly.
7. When does tracking start?
Support three configurable trigger types:
Account alert trigger: a detector creates an alert because one or more signals cross configured limits.
Transaction trigger: a transaction itself matches a configured high-risk pattern, such as an unusual burst or rapid onward movement.
Manual investigator trigger: the user selects an account or transaction and explicitly starts an investigation.
An off-ramp is not required to start tracking. It is a possible terminal marker. The trace can also stop at no more connected events, an investigation horizon, a hop/size budget, missing data, or unresolved attribution.
8. Lineage engine: backward + forward tracing
Implement as a graph traversal over posted/settled transactions, with time and amount constraints. Keep a clear distinction between direct transaction connectivity and estimated same-funds attribution.
Resolve the trigger to an account and/or transaction; record the trigger and the evidence that caused it.
Build candidate incoming and outgoing edges from eligible posted transactions. Exclude failed/pending transactions by default; include reversals as explicit correction events.
Backward pass: follow incoming transactions within a configurable look-back window to identify plausible upstream source accounts and earlier hops.
Forward pass: follow outgoing transactions within a configurable look-ahead window to identify plausible downstream destinations, repeated hops, and off-ramp events.
For each hop, record transaction ID, source/destination bank and account, amount, timestamp, status, and the rule/constraint that allowed the hop.
Handle splits and merges: one incoming transfer may be followed by multiple outgoing transfers; multiple incoming transfers may feed one outgoing transfer. Use bounded allocation candidates and show uncertainty where exact attribution cannot be established.
Deduplicate visits and detect cycles. A visited-state key should include account, direction, time boundary, and relevant amount/attribution state—not just account ID.
Stop on configured limits and record a machine-readable stop reason. Never silently truncate the graph.
Return nodes, edges, candidate paths, total traced hops, coverage, attribution confidence, and a plain-language explanation.
Stop reasons to support
OFF_RAMP_REACHED
NO_ELIGIBLE_INCOMING_OR_OUTGOING_TRANSACTIONS
LOOKBACK_OR_LOOKAHEAD_WINDOW_EXCEEDED
MAX_HOPS_REACHED
MAX_NODES_OR_EDGES_REACHED
MISSING_OR_CONFLICTING_DATA
AMBIGUOUS_AMOUNT_ATTRIBUTION
INVESTIGATION_CANCELLED
Performance expectations
Use indexed queries on source_account_id, destination_account_id, posted_at, status, and scenario_id.
Use bounded breadth-first traversal or a priority queue for ranked candidate paths; never recursively query the database once per edge.
Add configurable limits for maximum nodes, edges, hops, and runtime. Return partial results with a clear stop reason.
Target the demo scenario of 10,000 accounts and 100,000 transactions on a developer laptop; record actual runtime in evaluation rather than promising a specific SLA.
Do not claim that graph connectivity proves that the exact same money travelled through every edge. Show “direct transfer path” versus “estimated funds lineage.”
9. Off-ramp and terminal behavior
Represent an off-ramp as a synthetic event type, for example conversion to external cash/merchant payout/external rail, with a linked account and transaction.
Allow zero, one, or multiple off-ramps in a scenario.
If no off-ramp exists, trace until the graph ends or a configured boundary is reached. Label the result “trace ended; no off-ramp observed,” not “money exited.”
If a transfer leaves the simulated data boundary, show an external/unknown node and mark downstream lineage unavailable.
A threshold such as ₹1,00,000 may trigger extra scrutiny in a scenario, but must be configurable and not the sole detection mechanism.
10. Synthetic data and scenario factory
Create a deterministic scenario generator with a seed and hidden ground truth. Include realistic normal behavior alongside suspicious patterns so the system cannot pass by flagging everyone.
Scenario
Expected behavior
Simple mule chain
Source → mule A → mule B → recipient/off-ramp; detect and reconstruct all available hops.
Commission / retention
₹100,000 enters; intermediate account retains a configured percentage and forwards the remainder; show that exact attribution depends on ledger/allocation evidence.
Split flow
One inbound transfer is divided across several downstream accounts.
Merge flow
Funds from several sources converge into one account and later disperse.
Long chain
Hundreds or thousands of hops within configured limits; bounded traversal, performance and stop reason are tested.
Cross-bank chain
Every hop can cross a different synthetic bank; bank changes must not break lineage.
No off-ramp
Suspicious activity exists but no off-ramp event occurs; still detect and trace to boundary.
Multiple off-ramps
A network branches into multiple terminal events.
Fan-in / fan-out
Many-to-one then one-to-many movement.
Cycle / circular movement
A path returns to a previously visited account; traversal terminates safely.
Legitimate lookalikes
Payroll, family transfers, merchant settlement, refunds, subscriptions, charity, business cash management.
Low-and-slow
Activity spread across a long window rather than a burst.
Near-threshold
Amounts just below, at, and above a configurable threshold.
Pending / failed / reversed
Only eligible posted movement contributes to settled lineage; reversals are represented correctly.
Duplicate / idempotent request
Retries do not double-count the transfer.
Out-of-order events
Late events trigger a reproducible recomputation or update of investigation results.
Missing / conflicting data
Show incomplete evidence and uncertainty instead of inventing a path.
Disconnected components
Tracing does not wander into unrelated graph regions.
High-volume hub
A legitimate high-degree merchant or aggregator should not automatically be flagged.
Adversarial evasion
Vary amounts, split transfers, add delays, use intermediaries, or cross banks; evaluate degradation without hardcoding the answer.

The scenario generator must expose scenario metadata to the UI but never expose ground-truth labels to detector code. Evaluation code may compare output with labels after detection is complete.

Summary metrics: accounts discovered, banks crossed, transactions traversed, hops, off-ramps found, trace coverage, unresolved branches.
Show each hop as an evidence row: from → to, bank → bank, amount, timestamp, transaction ID, status, attribution method/confidence.

F. Scenario Lab & Evaluation
Scenario catalogue with expected purpose, network size, and Run button.
Ground truth is hidden during normal interactive detection; evaluation report may compare after run.
Compare baseline detector and Mule Matrix candidate on the same scenario seeds.
Metrics: account-level precision/recall/F1, false-positive rate on legitimate accounts, alert rate, lineage edge/path recall, source/terminal recovery, attribution error where ground truth supports it, runtime, node/edge count.

G. Settings / Rules
Editable detector thresholds, time windows, risk-score weights, lineage hop/node/time budgets, and simulation settings.
Validate inputs; show which detector version/config was used for each alert and evaluation run.
Provide reset-to-defaults and export/import configuration.
Visual design direction
Professional fraud-operations console, dark navy/charcoal base with restrained teal and amber accents; red reserved for high-severity alert indicators.
Prioritize graph readability and evidence over decorative animations. Motion should communicate a transaction or new discovery, not distract.
Responsive desktop-first layout; keyboard accessible controls, visible focus states, tooltips, loading/empty/error states.
Never rely on color alone: use icons, labels, line styles, and text for risk and edge types.

14. Test strategy and acceptance criteria
Correctness
A normal transfer creates one immutable transaction and does not duplicate on retry.
A suspicious scenario produces an alert only when its configured detector evidence supports one; every alert has at least one evidence record.
A no-off-ramp scenario still produces an investigation when a trigger exists, and ends with a correct no-off-ramp stop explanation.
Backward and forward traversal return the expected connected eligible transactions for deterministic chain, split, merge, and cross-bank fixtures.
Cross-bank hops work without special-case assumptions about bank identity.
Pending/failed transfers do not count as settled money movement; reversals adjust effective flow without deleting history.
Cycles terminate; high-degree nodes and long chains respect configured limits and return explicit stop reasons.
The lineage engine never attributes more value to a source lot than the amount available in the simulated allocation model.
Unknown or missing data is reported as uncertainty, not filled with invented accounts or transactions.
UI numbers and graphs match backend responses; all main buttons perform real actions and surface errors.
Evaluation uses held-out scenario seeds; ground-truth labels are unavailable to detector execution.
All tests pass from documented commands; setup works from a clean clone.
Security and quality
Validate all IDs, amounts, pagination, time windows, and configuration values.
Use environment variables for secrets; do not commit credentials. MVP should need no third-party API key.
Use structured logs and a request ID; never log real personal data because none should be present.
Provide database migrations and deterministic seed scripts.
Use frontend loading, empty, success, and error states; avoid swallowed exceptions.
Add backend unit tests for every rule and lineage stop reason, API integration tests, and frontend tests for transfer submission, alert evidence, and investigation navigation.

16. Demo walkthrough for judges
Open the synthetic environment and choose “Cross-bank split-and-merge mule network.”
Start the simulation; watch the initial transfer and subsequent account-to-account movements appear in the event feed.
Show the alert: the account is flagged because of named signals and visible evidence, not because the scenario is secretly labeled as a mule.
Open the investigation and run backward/forward tracing. Highlight the origin candidate, intermediary accounts, partial flows, cross-bank edges, and terminal/off-ramp if present.
Switch to a scenario with no off-ramp and show that tracing still works and explains why it stopped.
Run a legitimate lookalike scenario and show that the detector does not simply flag every high-volume account.
Open Evaluation and compare baseline vs candidate metrics on held-out seeds, including false positives and lineage recovery.
Export the case report containing the evidence, graph summary, trace stop reason, detector version, and limitations.
17. Important edge cases that must not be ignored
Case
Required behavior
Same account as source and destination
Reject unless explicit supported event type; never create accidental self-loop transfers.
Zero/negative/too-large amount
Reject with validation error.
Duplicate API request
Idempotently return original transaction.
Transaction timestamp out of order
Store event time and ingestion time separately; recompute affected traces if configured.

Preserve original and reversal link; update effective flow consistently.

Model fee and remainder explicitly; do not assume full amount moves onward.
Concurrent transfers
Use database transactions/locking or consistent ledger rules to avoid overspending if balances are enforced.

Keep edge but mark institution unknown; don't infer it.

Allow historical tracing; block new transfers if closed.

20. Definition of done
Mule Matrix MVP is done when a judge can clone/open the project, start the services, load a synthetic scenario, submit or replay transfers, see evidence-based account alerts, open an investigation, trace backward and forward across synthetic banks through splits/merges, handle a scenario with no off-ramp, inspect uncertainty and stop reasons, and compare the detector against a baseline on reproducible held-out tests. The UI must be connected to real backend behavior, the tests must pass, and the demo must clearly distinguish simulated capability from real-world bank access.
